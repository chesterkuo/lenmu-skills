# sd-script-engine · 劇本創作與小說改編引擎

## 一、角色定位

把用戶提供的小說、網文章節、故事大綱或已有劇本，改編成來源可追溯、人物有記憶點、全局設定穩定、分集完整、台詞可演、上下集自然銜接且經過獨立質量審核的專業**文字劇本**項目。

本引擎是六階段編劇鏈（來源登記 → IP 與角色開發 → 全劇開發聖經 → 分集規劃 → 正式劇本 → 五席圓桌審核）的唯一權威執行者。只交付劇本開發成果；不生成資產庫、角色資產 ID、導演分鏡、燈光剪輯方案、視頻提示詞、圖片、音頻或視頻。

## 二、與總控和套裝的關係

- 完整管線從總控 **short-drama-director** 進入：總控鎖系統（**〇·1 素材來源** / A·模型 / B·畫幅 / C·交付 / D·段縫）先鎖定，再進入本引擎；本引擎行文只寫「按總控鎖系統執行」，不重複定義鎖系統。
- **〇·1 素材來源為 ③ 對標爆款 / ④ 熱點速成 時**，`sd-recon-engine` 先出《對標情報卡》並經用戶確認，再進本引擎（見 §五·第 -1 步）。**《對標情報卡》是"來源"不是"設定依據"**——本引擎在「① 來源登記」保留其來源與分級（T1/T1.5/T2），**不得把 T2 討論升格為事實、不得把卡中「推斷」升格為「事實」、不得把同一稿的轉載算成多個獨立來源**。
- 本引擎只負責管線的「**文字劇本**」階段。六階段全部批次經用戶接受後，劇本交付物（含 HANDOFF_CARD 與禁改項清單）交給 **sd-asset-engine** 進入資產鎖定，隨後才是分鏡、打戲、投餵封裝與質檢。
- 總控已有的**五階門控劇本引擎**與**台詞七維診斷**繼續有效。本引擎的六階段鏈是它的**上游擴展**：六階段產出鎖定分集卡與鎖定劇本後，回到總控門控體系做終檢；台詞寫作以總控台詞七維診斷為準繩，本引擎規則庫中的台詞規則與其**配合使用**，不另立標準。
- 投餵格式（七段式）、機檢腳本（validate_prompt.py）、「圖N」資產編號體系、《資產圖冊》《劇組產出冊》台賬的唯一權威都在總控；本引擎在任何階段都不得另立投餵格式或資產編號。

## 三、觸發詞與進入

觸發詞：寫劇本、改編小說、小說轉劇本、劇本改編、分集、分集規劃、開發聖經、故事聖經、IP開發、劇本審核、圓桌審核、劇本精修、圓桌評審。

用戶直接說「寫劇本 / 改編小說 / 小說轉劇本」等觸發詞且尚未在完整管線中時，先聲明：完整製作（資產、分鏡、視頻）請從總控 short-drama-director 進入；**並先確認素材來源（〇·1：1 原創 / 2 改編 / 3 對標爆款 / 4 熱點速成）——該鎖未確認不進入創作**；本引擎只完成文字劇本鏈，產出後可繼續走 sd-asset-engine。

自動識別輸入是完整小說、小說節選、大綱、已有劇本或續接項目；自動識別已有交付物和當前最後鎖定階段，不要讓用戶手工說明內部階段編號。模式未確定前只登記來源和識別材料類型，不生成正式 IP。用戶已經明確模式時不得重複詢問。

## 四、來源與事實權威鏈

始終遵守：

`用戶提供的小說事實 > 鎖定IP > 鎖定故事聖經 > 鎖定分集規劃 > 當前劇本 > 圓桌意見`

區分 `FACT`、`INFERENCE`、`ASSUMPTION`、`USER_OVERRIDE` 和 `OPEN_ITEM`。不得把市場套路、評審偏好或模型推斷改寫成小說事實。允許壓縮、合併、可視化、用戶授權重排和不改變核心事實的連接材料；禁止自由新增關鍵身份、能力、證據、關係、規則、勝負、謎底或結局。

## 五、工作流程：前置素材來源鎖確認 → 外來劇本檢測 → 模式選擇 → 六階段 → 門禁

### 第 -1 步：前置素材來源鎖確認（〇 · 1 · 先於模式選擇）

**本步在全流程最前面，任何模式選擇與創作之前完成。** 素材來源規程以總控 §〇·1 與 `sd-recon-engine/SKILL.md` 為準。

```text
請先確認一件事（前置鎖 · 先於模式選擇）：

〇·1 素材來源（第 1 道鎖）：
1. 原創       —— 從零構思
2. 改編       —— 已有小說 / 網文 / 大綱 / 劇本
3. 對標爆款   —— 指定一部劇，先採風出《對標情報卡》
4. 熱點速成   —— 只給方向，先找選題方向

回覆示例：3（對標爆款）
```

**〇·1 素材來源執行要點**：

- **未確認前，不進入第 0 步模式選擇**——不登記來源、不生成 IP / 分集 / 正文；
- **③ 對標爆款 / ④ 熱點速成**：**先掛載 `sd-recon-engine` 出《對標情報卡》並經用戶確認**，再進第 0 步模式選擇——**情報卡未確認 = 不進入創作**（對標不是照抄：情報卡的「⑩ 可遷移點 / ⑪ 不可遷移點」才是本環節的產出核心；只填熱度不填遷移點 = 白採）；
- **④ 熱點速成**：採風產出的是**"選題候選"**而非單劇卡；用戶選定方向後按所選方向回到 ① 或 ③ 執行；
- **① 原創 / ② 改編**：**不掛載採風引擎**，直接進入第 0 步（**不額外增加步驟**）；
- **情報卡進入「① 來源登記」時**必須保留**來源與分級（T1 一手 / T1.5 準一手 / T2 二手）**；**禁止把 T2 討論當設定依據、禁止把卡中「推斷」寫成「事實」**。

**素材來源寫入項目狀態**（`SCRIPT_PIPELINE_STATE.json` 與 `PROJECT_MANIFEST.md`），後續階段不再更改。

### 第 -0.5 步：外來劇本檢測與潤色層（★ 2026-10-13 新增 · 只在「成型劇本」輸入時觸發）

**本步位於前置雙鎖之後、模式選擇之前。判定口徑（三條同時看）：**

```text
〇·1 = ② 改編 且 輸入物是「已成型的劇本」（有場次劃分 + 台詞行）
        ↓
外部劇本體檢（五條，命中 ≥1 即觸發）
□ 台詞行只有「角色：台詞」、無（語氣）位、鏡行無神態？
□ 動作提示是結果性的、無過程相位？
□ 無狀態欄（人物狀態/情緒/傷勢/道具位置）？
□ 關鍵台詞無重音標註？
□ 相鄰場次無因果連接？
        ↓
命中 → 掛載【外部劇本潤色層】→ 產出潤色稿 + 回籤卡 → 用戶確認 → 才進 P2/P3
全不命中（外部劇本已自帶表演層）→ 免走，直接進 P2/P3（交接卡首行聲明「免潤色」）
```

- **規程唯一權威**：[external-script-polish.md](references/external-script-polish.md)；
- **潤色邊界（硬約束）**：**只補表演層（神態/動作相位/視線/語氣位）+ 調度層（站位/進出場/過渡）**；⛔ **不得改台詞、不得改事件、不得改人物**——那是越權重寫；
- **發現硬傷**（人物降智 / 因果斷裂 / 時間線矛盾）**只報告不修改**，出《潤色發現清單》交用戶裁定；
- **潤色產出必須回籤**——補出來的表演層是創作決定，用戶逐條確認後才進 P3；
- **不適用**：〇·1 = ① 原創，或輸入是小說/大綱/梗概（這兩類走完整六階段鏈，產出即自帶表演層）。

### 第 0 步：模式選擇

新項目尚未選擇模式時，只顯示：

```text
請選擇製作模式：
A. 逐步確認（推薦）：每一步完成後由你確認，再繼續下一步。
B. 完整執行：自動完成IP、全局開發、分集與劇本；每批劇本審核後仍暫停等待你選擇。

回覆示例：
- 回覆：A
- 回覆：B
```

### 六階段鏈

```text
前置鎖 〇·1 素材來源   → 總控 §〇·1（③④ 先經 sd-recon-engine 出《對標情報卡》並經用戶確認）
→ 外來劇本檢測（-0.5）   → 僅在「成型劇本」輸入時觸發 → references/external-script-polish.md（潤色層 + 回籤）
→ 模式選擇                 → 本文件第 0 步
→ ①來源登記               → references/source-registration.md
→ ②IP 與角色開發         → references/story-bible-and-ip.md（IP 部分）
→ ③全劇開發聖經           → references/story-bible-and-ip.md（聖經部分）
→ ④分集規劃【分集選擇門】  → references/episode-planning.md
→ ⑤正式劇本【按批生產】    → references/six-stage-pipeline.md 第⑤階段（★ 第 8 道工序「台詞改寫」前必過**台詞擬人化過站** → references/dialogue-naturalization.md）
→ ⑥五席圓桌審核【用戶決策門】→ references/roundtable-review.md
→ 用戶決定：接受 → 下一批或完成劇本包；修改 → 一次精修/重寫 → 回到⑥

※ 素材來源③④：《對標情報卡》進入 ①來源登記 時保留來源與分級（T1/T1.5/T2），
   T2 討論不得當設定依據、卡中「推斷」不得升格為「事實」。
```

每階段：進入條件 → 生成全部文件 → 按階段校驗清單逐項自檢 → 鎖定或 `AWAITING_CONFIRMATION`。各階段進入條件、產出物與門禁的完整定義見 [six-stage-pipeline.md](references/six-stage-pipeline.md)。

### 項目狀態

每個項目創建：

- `projects/<project-id>/SCRIPT_PIPELINE_STATE.json`
- `projects/<project-id>/PROJECT_MANIFEST.md`
- `projects/<project-id>/00_source/SOURCE_MANIFEST.json`

階段狀態只允許：`NOT_STARTED / IN_PROGRESS / AWAITING_CONFIRMATION / AWAITING_USER_DECISION / LOCKED / STALE / BLOCKED`。鎖定輸入發生改變時，從變更階段向下傳播 `STALE`，不得靜默沿用舊版本。

### 分集選擇門

階段④開始前，用戶未明確集數方式時提供：`1. 智能推薦集數（推薦）` / `2. 用戶自定義集數`（如「2，60集」）。用戶只回復 2 沒有數字時，提示「請告訴我想製作的總集數，例如：60集」，不得提前排集。內部只記錄 `SMART_RECOMMENDED` 或 `USER_DEFINED`。詳見 [episode-planning.md](references/episode-planning.md)。

### 圓桌審核與用戶決策門

階段⑥固定模擬兩名主編和三類觀眾，必須標註 `AI_ROLE_SIMULATION`。五席先獨立審讀，再討論並按固定權重計算 `S/A/B/NOT_READY`；等級只代表劇本層潛力，不預測真實播放量。任何等級統一寫 `decision: AWAITING_USER_DECISION`，並顯示：

```text
請選擇：
1. 接受當前版本，進入下一批或完成劇本包。
2. 進行一次精修或重寫，修改後提交下一輪審核。

回覆示例：
- 回覆：1
- 回覆：2
```

`B/NOT_READY` 選擇 1 時必須明確記錄 `USER_ACCEPTED_QUALITY_RISK`，等級保持原值。沒有用戶選擇時不得自動修改、寫下一批或宣佈項目通過。詳見 [roundtable-review.md](references/roundtable-review.md)。

### 精修與複審

只有用戶選擇 `REFINE_OR_REWRITE` 記錄後才能進入精修/重寫。精修團隊必須先讀原小說、IP、故事、分集和當前劇本，最後讀評審意見；根據根因選擇 `LOCAL_POLISH`、`EPISODE_REWRITE` 或 `BATCH_REWRITE`。一次授權只生成一個正式新版本，目標 S、最低爭取 A，但不保證等級、不追分魔改。修改後提交新一輪盲審；複審結束再次等待用戶選擇。詳見 [six-stage-pipeline.md](references/six-stage-pipeline.md) 第⑦節。

### 長劇批次合同

正式劇本按連續集數分批，默認根據內容容量選擇每批大小。每批必須：

- 讀取本批全部來源原文、上一批末集完整劇本和連續性賬本。
- 保存入口狀態、變化、出口狀態、鉤子債務和下一批第一動作。
- 每集單獨點開能看懂，同時上一集最後變化直接觸發下一集第一動作。
- 首場前 10 秒包含來源支持的爆點、最小處境、行動問題和 `WHY_NOW`。
- 先形成局部兌現，再落具體且可支付的下一集鉤子。

批次無法一次顯示時繼續寫入項目文件，不壓縮成梗概或碎片化節拍。

## 七、階段校驗方式

本技能不帶獨立機器校驗腳本；各階段的機器校驗項（IP 十二項質量門、故事十五項質量門、分集質量門、劇本二十五項鎖稿門、圓評六項硬門）一律轉為**階段校驗清單**，由執行者逐項人工核對，全部 `PASS` 且 `failure_flags` 為空才能鎖定。失敗標記不得手工清空；先修改正文或賬本，再重新逐項核對。缺少原小說、鎖定上游、用戶授權或連續性證據時輸出 `BLOCKED_REPORT`。

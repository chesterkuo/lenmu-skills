# 六階段編劇鏈總流程

> 精編自《靈境AI劇本改編 skill》（6階段編劇鏈）

本文件是 sd-script-engine 的主流程權威：六階段的進入條件、產出物、門禁，兩種製作模式，第⑤階段正式劇本的完整寫作規範，以及授權後的精修/重寫。各階段的專項細則路由到其餘四份規則庫。

## 一、六階段總覽

```text
①來源登記 → ② IP 與角色開發 → ③全劇開發聖經 → ④分集規劃 → ⑤正式劇本 → ⑥五席圓桌審核
→ 用戶決定〔接受，或 精修/重寫（04F）→ ⑥〕
```

到用戶接受全部劇本批次為止。禁止在本鏈內創建資產庫、角色資產 ID、導演分鏡、燈光剪輯方案、視頻提示詞、圖片、音頻或視頻。

### 事實權威鏈（全鏈適用）

`用戶提供的小說事實 > 鎖定IP > 鎖定故事聖經 > 鎖定分集規劃 > 當前劇本 > 圓桌意見`

區分 `FACT`、`INFERENCE`、`ASSUMPTION`、`USER_OVERRIDE` 和 `OPEN_ITEM`。市場套路、評審偏好或模型推斷不得改寫成小說事實。

### 階段門禁與校驗方式

- 每階段只消費已鎖定（`LOCKED`）並通過校驗清單的上游成果；上游 `STALE`、版本不一致或來源覆蓋不完整時停止並報告。
- 階段校驗一律按「階段校驗清單」逐項人工核對（見 SKILL.md 第七節）：全部 `PASS` 且 `failure_flags` 為空才能鎖定；失敗標記只能通過修改正文或賬本消除，不得手工清空數組。
- 任何新批次都以文件賬本為權威，不依賴聊天窗口保留完整上下文。

## 二、兩種製作模式

### A. 逐步確認（STEPWISE）

每次只完成一個未鎖定階段：

1. 檢查來源和上游版本。
2. 完整讀取當前階段規則庫和必讀章節。
3. 生成該階段全部文件。
4. 執行語義自檢和階段校驗清單核對。
5. 置為 `AWAITING_CONFIRMATION` 並停止。

用戶確認後才鎖定並繼續。階段④開始前另行執行分集選擇門；階段⑤按連續批次生產，每批完成後必須進入⑥。

### B. 完整執行（FULL_SCRIPT_PIPELINE）

自動執行階段②—⑤，但仍遵守所有鎖定門：

- 階段②—③校驗清單失敗立即停止。
- 用戶未指定集數時，階段④使用智能推薦。
- 用戶指定集數超出容量區間時，必須暫停說明代價並取得二次確認。
- 長劇仍按連續批次寫作，不能依賴聊天窗口維持狀態。
- 每批⑥結束後無條件暫停；完整執行不代表可以替用戶決定是否修改。

## 三、階段①來源登記（摘要）

進入條件：用戶已提供全部材料，模式已選定。

核心動作：建立 `SOURCE_MANIFEST.json`（每塊記錄 `source_id`、標識、章節起止、範圍、內容哈希、讀取/提取/合併狀態）；自動識別材料類型（完整小說/節選/大綱/已有劇本/續接項目）；長篇按自然章節邊界分塊做 P1/P2 事實提取；同時啟動全篇角色證據掃描。

產出：`00_source/SOURCE_MANIFEST.json`、`PROJECT_MANIFEST.md`、`SCRIPT_PIPELINE_STATE.json` 初始化。

門禁：全部已提供來源完成登記與哈希、別名和時間狀態衝突已處理、`unresolved_ranges` 為空。細則見 [source-registration.md](source-registration.md)。

## 四、階段② IP 與角色開發 與 階段③全劇開發聖經（摘要）

- ② IP 與角色開發：從來源提煉角色 IP（S/A/B/C 層級、靈魂引擎、觀眾喜愛路徑、五類記憶點、關係專屬性、表演聲音、視覺身份、成長地圖、類型適配），交付 `01_ip/` 六件套（`01_IP_BIBLE.md`、`IP_CANON_MANIFEST.json`、`VISUAL_IDENTITY_BIBLE.md`、`STYLE_PROFILE.md`、`IP_PRESENTATION_PACKAGE.md`、`HANDOFF_CARD.md`）。門禁：IP 十二項質量門全 PASS。
- ③全劇開發聖經：三遍通讀（觀眾/事實/改編）+ P1/P2/P3 流程，建立創意 DNA、類型受眾合同、四層梗概、世界觀價值合同、人物故事小傳、大弧架構、七類改編藍圖、鉤子候選池與容量診斷，交付 `02_story/` 十件套。門禁：故事十五項質量門全 PASS；`exact_count_locked` 必須為 `false`。**★ 另必須附《世界錨卡》與《人物錨卡》**（`story-bible-and-ip.md` §1.11）——**世界錨卡＝年份/地域/技術時代 + 禁用元素清單 + 必現元素清單；人物錨卡＝年齡段 + 身高體型 + 身份外觀三件套（職業標識物/服裝形制/氣質體態）+ 反漂移清單**。二者抄進 `HANDOFF_CARD.md` 禁改項隨稿傳下游；**缺任一張 = 階段③ 未完成**（由來：粉絲實測「2035 年南京出片成 80 年代破街爛車、外賣員出成協警、年齡與身材比例卡不到」）。

完整規範見 [story-bible-and-ip.md](story-bible-and-ip.md)。

## 五、階段④分集規劃（摘要）

進入條件：①—③已鎖定，分集選擇門已過（`SMART_RECOMMENDED` / `USER_DEFINED`）。

核心動作：九遍策劃流程——鎖定精確集數、標註事件歸屬與可壓縮性、建立開篇爬坡與大弧、建立完整單集故事單元、觀眾理解契約、局部兌現與追看契約、情緒與 IP 編排、邊界連續性防重複、三種觀眾終審。

產出：`03_episodes/` 六件套（`03_EPISODE_PLAN.md`、`EPISODE_PLAN_MANIFEST.json`、`VIEWER_RETENTION_MAP.md`、`EVENT_COVERAGE.md`、`HOOK_PAYOFF_LEDGER.md`、`HANDOFF_CARD.md`）。

門禁：每個事件唯一主歸屬；每集理解/行動/兌現/追看/情緒/連續性/IP 字段完整；鉤子種下集與兌現集一致；不存在連續三集同一衝突公式；全部質量門 PASS。細則見 [episode-planning.md](episode-planning.md)。

## 六、階段⑤正式劇本：原作忠實劇本主編

> 本節為第⑤階段的完整寫作規範。台詞規則與總控「台詞七維診斷」**配合使用**：總控七維為準繩，本節規則補充劇本層執行口徑，二者衝突時以總控裁定為準。

### 6.1 核心結果

把小說內容「劇本化升級」，不是脫離小說重新編故事。正式劇本必須同時滿足：

1. 原作主線、人物動機、關鍵關係、世界規則、關鍵因果、趣味看點和關鍵台詞功能不丟。
2. 每集是能連續複述的完整故事單元，不是梗概、節拍清單、名場面拼貼或一場戲的上下半段。
3. IP 靈魂選擇、缺點後果、專屬行為、人物聲音和關係信號進入正文行動，不靠設定說明代替。
4. 衝突由目標、策略、反制、換策和代價推進；先兌現本集所得，再落下有兌現位置的主鉤子。
5. 長劇可分批、分集交付，但批次邊界不能改變全劇方向、人物狀態、時間線、伏筆或鉤子債務。
6. 每集同時滿足連續觀看與單集觀看：首場前 10 秒有來源支持的爆點、最小處境、行動問題和 `WHY_NOW`，上一集最後變化直接觸發下一集第一動作。

### 6.2 門禁與輸入

只消費已鎖定並通過校驗的階段①—④：`PROJECT_PROFILE`、`01_IP_BIBLE`、`IP_CANON_MANIFEST.json`、`IP_ARC_BINDINGS`、`02_STORY_BIBLE`、`STORY_CANON_MANIFEST.json`、`03_EPISODE_PLAN`、`EPISODE_PLAN_MANIFEST.json`。

若上游版本、人物 ID、事件 ID、集數或鉤子賬本不一致，立即停止並輸出 `BLOCKED_REPORT`。不得憑記憶補齊衝突版本。

每集必須完整消費 `episode_thesis`、`one_sentence_recall`、`story_unit`、`comprehension_contract`、`retention_contract`、`emotion_curve`、`timeline`、`ip_dramatization`、`primary_events`、`callbacks` 和 `source_trace`，不能只讀取集標題或一句摘要。

`STEPWISE` 只寫用戶確認的集數或批次。`FULL_SCRIPT_PIPELINE` 同樣一次只完成一個連續批次；本批校驗通過後輸出交接包並停止，由總控單獨發起圓桌評審。任何模式都不得繞過審核後的用戶質量選擇繼續寫下一批。

### 6.3 來源權威鏈與退回規則

事實權威從高到低：`小說原文 → 故事聖經 → 分集卡 → 正式劇本`。

階段⑤每寫一集都必須重新讀取該集 `source_trace` 對應的小說原文、關鍵台詞原文和必要前後文，不能只看摘要繼續擴寫。

若要改變以下任一內容，退回階段④修訂並重新鎖定，不得在劇本里靜默修改：

- `primary_events`
- `episode_thesis` 或 `one_sentence_recall`
- `local_payoff`
- `primary_hook_id`、`payoff_episode` 或 `next_episode_first_action`
- 核心角色及 IP 版本
- 事件事實生效順序、人物知識邊界或來源壓力條件

允許的改編動作（每項來源內容只能標記一種）：

- `KEEP`：保留事實、功能和發生條件。
- `COMPRESS`：壓縮重複敘述或過程，但保留因果、動機、代價和結果。
- `MERGE`：合併同功能過程、場次或次要人物功能，不改變責任與關係位置。
- `VISUALIZE`：把心理和敘述轉成可見行動、反應、空間、道具或策略對白。
- `REORDER_AUTHORIZED`：只執行上游已授權的重排，並保護知識邊界和事實生效順序。
- `DELETE_REDUNDANT`：刪除無獨立功能的重複內容，並完成刪減影響審計。
- `CONNECTIVE_INFERENCE`：補充不改變主線事實的入場、移動、反應、職業流程和連接對白。

禁止新增或替換原作的關鍵身份、能力、秘密、證據、規則、關係、責任、勝負、謎底和結局；禁止用流行套路覆蓋原作人物；禁止把「可能、以後、條件成立」擅自寫成「已經、現在、必然」。`MUST_KEEP` 與本集 `primary_events` 不得標記 `DELETE_REDUNDANT`。任何刪減都要證明因果鏈、人物動機、伏筆回收、關係變化和後續理解沒有斷裂。四級比對、刪減影響審計與關鍵台詞保護的完整規範見 [source-registration.md](source-registration.md) 第三、四節。

### 6.4 主筆標準（head-writer-standard）

短劇主編對「項目能否持續兌現受眾承諾並被生產執行」負責，不只是修改幾句台詞。

**立項與受眾承諾**：把題材標籤改寫成可檢驗的受眾承諾；判斷一句話賣點是否包含人物、異常處境、行動目標和失敗代價；明確創新點改變的是衝突機制還是人物選擇；設定開篇證明、階段兌現和最終情感回收，保證前期賣點與結局不是兩部作品。

**編劇室與長劇分批管理**：主編向編劇室提供已鎖定的 IP、故事聖經、事件覆蓋、分集卡、人物聲音和版本號；每位編劇只在獲分配集數內創作。交稿時必須附：本集承諾、來源事件、狀態變化、鉤子兌現、疑問項和改動影響。主編統一：人物稱呼、語氣、秘密和知識邊界；道具歸屬、傷勢、服裝、地點和時間連續性；同一伏筆的種下、提醒和回收措辭；大弧節奏、商業節點與情感主線；場次格式、時長估算和版本命名。發生上游改動時先標記受影響劇本為 `STALE`，列出受影響集數，不允許口頭改完後繼續沿用舊清單。

**七輪審稿**（逐集鎖定前依次執行，任一輪 `REVISE`/`REWRITE` 先改正文再複審）：

1. **來源、故事與因果**：核對四級來源、改編動作和刪減審計，再檢查目標、阻力、策略、反制、轉折、局部兌現和鉤子。主角必須主動做事；反轉必須有來源或已建立證據；爽點必須有準備、見證和結果。
2. **人物與關係**：行動是否來自角色慾望、恐懼和當前信息；對手是否有有效目標；關係場是否改變下一步選擇。人物突然變蠢、突然全知或突然變心時退回重寫。
3. **台詞與表演**：逐句標註功能，檢查角色聲音、潛台詞、搶話、停頓和可見反應；抽取主語、對象、條件與後果確認可複述；刪除重複解釋和可被動作替代的說明；關鍵情感台詞前後要有行為支撐。
4. **連續性與格式**：核對集號、場號、內外景、日夜、出場人物、入場/退出狀態、人物知識、傷勢、道具、界面/文件首次出現和承接動作。執行 `STANDALONE_EPISODE_TEST`、`LAST_FRAME_FIRST_ACTION_TEST` 和 `FLASHBACK_ANCHOR_TEST`。
5. **桌讀、時長與製作成本**：對白按角色語速朗讀，動作加入準備、反應和停頓。超時先去重複，再合併同功能場次。預算問題用場面調度和信息載體解決，不擅自刪主線。
6. **合規與風險**：審查自傷、極端暴力、未成年人、歧視羞辱、性暗示、違法模仿、真實人物肖像和聲音等風險；記錄問題、功能、替代呈現和上下游影響，再按項目尺度修訂。
7. **去元數據通讀與觀眾複審**：隱藏所有工作字段，只朗讀正文；以編劇、導演和第一次觀看的觀眾回答故事能否連續複述、衝突是否由行動推進、關係轉變是否有行為依據、代價是否真的發生。技術字段全部通過但正文像會議紀要時，仍應 `REWRITE`。

**判定標準**：`PASS`（七輪全過，可鎖定）/ `REVISE`（列出精確修改項後複審）/ `REWRITE`（核心目標不清、因果斷裂、人物失真、主事件被刪、鉤子無兌現或新增無來源重大設定；不能靠潤色通過）。

**主編不可做的事**：不能用流行套路覆蓋原作人物，不能把更高權力或更多財富當作唯一升級，不能把重複羞辱當衝突，不能為製造卡點拖延已經承諾的答案，也不能在劇本鎖定後不登記版本就要求下游繼續生產。

### 6.5 全劇先行：SERIES_SCRIPT_STRATEGY

第一集開寫前先創建 `04_scripts/SERIES_SCRIPT_STRATEGY.md`（寫作憲法），鎖定：

- 原始創意、題材機制、受眾承諾和全劇一句話行動線。
- 主線、情感線、成長線、關係線、謎團或任務線的優先級。
- 各大弧進入壓力、階段兌現、情緒回報和不可擅改事實。
- 核心人物慾望、恐懼、錯誤策略、靈魂選擇、缺點後果、聲音與關係動力。
- 題材專屬節奏：爽點/笑點/懸念/情感/動作如何建立、升級、見證和兌現。
- 關鍵台詞保護策略、來源壓力、伏筆回收、禁用套路和合規邊界。
- 默認單集時長、批次大小、相鄰集連讀方式和全劇終審條件。

策略文件只統一本劇寫法，不能創造小說中不存在的故事答案。

**八層全劇分析**：

1. **原始創意**：一句話說清最不可替代的想像，不寫題材標籤。
2. **受眾承諾**：分別定義情節回報（勝負、破解、成長、逆轉、關係變化）、情緒回報（爽、笑、甜、痛、燃、怕、好奇、治癒）、人物回報（為何想繼續看這個 IP 選擇、犯錯、付出和改變）。
3. **全劇行動線**：`誰為了什麼長期目標 → 持續面對什麼機制性阻力 → 採用什麼獨特辦法 → 失去或改變什麼 → 最終必須做什麼選擇`。
4. **多線優先級**：鎖定各線優先級和交匯點；只提供熱鬧但不產生後果的副線壓縮。
5. **人物發動機**：想要什麼、害怕什麼、習慣用什麼錯誤策略自保、壓力下暴露什麼缺點、哪類選擇最能證明靈魂核、與誰在一起時出現專屬關係動作和語氣。
6. **大弧兌現**：每個大弧必須有進入壓力、階段目標、升級方式、關係/情緒兌現、不可逆結果和進入下一弧的新問題。
7. **題材節奏**：節奏來自信息、選擇和結果的密度，不是鏡頭數量。速查表：

| 題材 | 核心推進 | 必須避免 |
|---|---|---|
| 逆襲/爽劇 | 能力或策略被建立、受阻、公開見證、兌現併產生新代價 | 無準備打臉、對手輪流降智 |
| 懸疑 | 公平線索、錯誤解釋、調查行動、證據改變判斷、答案分層支付 | 只靠藏信息、憑空證據 |
| 愛情/關係 | 需求衝突、邊界試探、具體付出、誤解有事實基礎、關係選擇改變行動 | 只靠誤會拖延、突然心動 |
| 喜劇 | 人物認真目標與錯誤策略碰撞、升級、回扣，笑點改變局面 | 與人物無關的段子拼貼 |
| 動作/戰鬥 | 目標、空間規則、能力限制、戰術變化、損傷和勝負後果 | 只有招式名和無代價碾壓 |
| 生存/末日 | 資源規則、團隊分工、道德選擇、環境反饋和長期後果 | 隨時刷出資源、規則臨時變化 |
| 玄幻/系統 | 規則建立、使用條件、反噬/代價、策略組合和成長門檻 | 臨場新增能力解決問題 |
| 家庭/年代 | 現實約束、關係責任、具體生活行動、尊嚴與利益選擇 | 現代價值口號替代時代行動 |
| 職場/商戰 | 職權邊界、流程、利益、證據、談判和結果落地 | 一句話讓專業系統失效 |

混合題材先確定主引擎，其他題材元素服務主引擎，不平均分配戲份。

8. **禁用捷徑**：登記本項目不可使用的寫法，如主角突然掌握未知信息、反派為送爽點公開自毀、關鍵人物靠旁觀直到最後一句才參與、每集重複同一羞辱—反擊公式、口頭禪和標誌動作機械簽到。

**批次策略**：推薦每批 3–8 集；單集特別長時縮小批次。每批必須明確入口狀態、本批共同推進的弧目標、每集不同的行動問題和衝突機制、本批至少一次真實兌現、出口狀態和下一批第一動作、本批承擔的伏筆與鉤子債務。不得為了「看起來有結尾」提前發明大答案，也不得把本批應支付的局部兌現全部推到下一批。

**長線穩定性抽查**（每批完成後）：主角是否仍由同一核心慾望驅動但策略在變化；**主角能力/認知盲區是否仍成立、認知是否被擊穿並改變行為**（`story-bible-and-ip.md` §1.9.1）；缺點是否造成真實後果；**對手是否根據此前輸贏調整策略、是否達到能力基線**（§6.5 反派能力基線）；關係變化是否累積、是否無故復位；**同一角色對同一對象的稱呼是否與 `ADDRESS_LEDGER` 一致、有無無因漂移**（一致性鐵律見 `dialogue-naturalization.md` §1.3；變化必須有事件觸發）；世界規則與能力限制是否穩定；**同一公式族（`pressure_pattern × resolution_pattern`）全劇是否 ≤3 次、每 10 集是否 ≤2 次**；**本批是否證明與「首 10 集衝突簽名基線」的差異**（`episode-planning.md` §5.8 四條去重鐵律）；每三集的衝突機制、情緒回報和結尾鉤子是否過度重複；重要伏筆、承諾和關鍵台詞是否按計劃支付；最近一批是否仍能用全劇一句話行動線解釋其必要性。任一答案為否，先修復最近受影響的最早一集，再向後重審。

**反派能力基線（★ 2026-10-13 新增 · 治「反派零智商、衝突一起當場被反殺」）**：

> **由來（粉絲系統性實測反饋）**：「反派**零智商**，衝突一起反派**基本當場被反殺**，套路化太嚴重」。
> **病根**：本包**禁令滿配、正向配額為零**——「不許降智」「不許對手輪流降智」「不許反派為送爽點自毀」等共 7 處，但**沒有任何一條規定「反派必須強到什麼程度」**。執行者只要「沒寫降智台詞」就能過關——而**「衝突一起就被反殺」本身不違反任何一條現有規則**。

三條正向配額（**進入階段③時與 `ARC_MAP` 同批鎖定，缺任一條即 `REVISE`**）：

1. **首次交手須佔上風或全身而退**——主角與主要反派**首次正面交手**時，反派**必須佔上風、或至少全身而退**；⛔ 不得首次交手就被反殺、或被壓制到毫無還手之力。**理由**：反派須先在觀眾心裡**立起來**，後面的翻盤才有分量。
2. **反殺前須 ≥3 輪博弈**——主角**反殺 / 翻盤**主要反派之前，須經過 **≥3 輪有效博弈**（**每輪** = 反派反制 → 主角換策 → 代價升級）。⛔ 不得「一碰就倒 / 一輪秒殺」。
3. **同一反派被擊敗前至少贏過 1 次**——同一主要反派在被擊敗前，**至少要有 1 次明確的勝利或得手**（奪走主角某物 / 逼主角讓步 / 造成不可逆損失）。⛔ 全程捱打的對手不成立。

⚠️ **與上游禁令配套（不放鬆，只補下限）**：本條**不放鬆**任何既有禁令——`FORBIDDEN_CHANGE`「把對手降智以便主角贏」、禁用捷徑「反派為送爽點公開自毀」照舊生效。**它補的是"反派強度的下限"，不是"打贏的上限"**。**敵強 → 我方智取 → 才叫爽；敵弱 → 隨手碾死 → 叫注水。**

⚠️ **與公式去重聯動**：**反派強度不升級，是公式重複的根本原因**（同一個弱對手換個名字再來一遍）——本條與 `episode-planning.md` §5.8 的公式族配額、階段升級義務**必須同時達標**。

⚠️ **主角受挫配額（配套）**：全劇前 1/3 段，主角**必須至少經歷 2 次真實失敗或重大受挫**（失去盟友 / 失去資源 / 判斷失誤造成損失），且**每次失敗都改變下一步策略**。⛔ 全程零挫折的"順風順水"不成立——**沒有低谷的高潮是廉價的**。

### 6.6 場次因果、觀眾理解與跨批連續性（scene-causality-and-audience）

**完整劇本的最小單位**：每一場必須有人帶著具體目標進入，並因對手、規則、環境或關係對象的反應而改變做法。有效場次至少形成：

`目標 → 首次策略 → 主動反制 → 轉折/新信息 → 決定或代價 → 狀態變化`

場次結束時至少改變一項：目標、關係、信息、資源或危險。沒有變化的場次是說明、重複或氣氛，應與行動場合並或刪除。

**場次因果圖**（每場在審稿層記錄）：

```yaml
scene_id: EP001-SC01
source_event_ids: ["EVT-0001"]
objective: "主角要拿回被扣的報名表"
counter_objective: "老師要逼他公開認錯後才歸還"
first_strategy: "私下說明證據"
counteraction: "對方當眾宣讀處分決定"
turn: "主角發現處分日期早於事件發生"
decision_or_cost: "他放棄私下解決，承擔公開對抗後果"
result: "報名表仍未取回，但處分程序被迫暫停"
exit_change: "秘密衝突變成公開質疑"
causes_next: "教導主任要求當場調檔，進入 SC02"
duration_seconds: 32
```

下一場必須由上一場結果、決定或新壓力觸發。只有「與此同時」的平行線也要說明它為何此刻切入，以及回到主線時改變什麼。

**觀眾理解合同**（每集寫入審稿層）：

```yaml
audience_contract:
  who_wants_what: "誰想完成什麼"
  obstacle_and_change: "阻力如何迫使換策"
  local_payoff: "本集已支付的結果"
  emotion_payoff: "觀眾得到的情緒回報"
  one_sentence_recall: "普通觀眾可複述的一句話"
  next_click_reason: "為什麼必須看下一集"
```

「危機升級」「真相浮現」「兩人爭吵」不是合格複述；必須包含人物行動和結果。

**反碎片化讀法**：隱藏所有來源字段、節拍標籤、場次目標、功能標籤和審稿結論，只讀場頭、動作和台詞。連續正文應自然形成 `因為前一事實/選擇 → 所以人物行動 → 但是遭到反制 → 於是改變策略 → 結果局面發生變化`。每段都像預告片金句、連續「看見、震驚、發誓」而無人改變行動、場景頻繁切換隻增地點不增狀態、重要結果在場間跳過、集尾機械截斷——都是碎片化表現。

**節奏控制**：約 90 秒可參考——進入與目標 10–15 秒、首次行動與反制 25–35 秒、換策與升級代價 25–35 秒、局部兌現與主鉤子 15–25 秒。不是硬分配；鉤子位置和故事節點優先。超時處理順序：刪重複信息 → 壓縮同功能對白 → 合併同地點同目標場次 → 把解釋嵌入有衝突的行動 → 保留動機、反制、選擇、代價、局部兌現和必要反應。

**跨集與跨批連續性**：`CONTINUITY_LEDGER.json` 至少維護 `characters`（位置、身體、情緒、目標、已知、誤解、秘密和承諾）、`relationships`、`props`、`timeline`、`hooks`、`foreshadowing`、`batches`（每批入口、變化、出口和下一批第一動作）。每批開始先驗證 `上一批出口狀態 = 本批入口狀態`，不一致時標記 `CROSS_BATCH_STATE_DRIFT`；本批所需關鍵狀態只存在於聊天記憶時標記 `BATCH_CONTEXT_GAP`。

**逐集四級審稿**（每集鎖定前按順序問）：小說對故事聖經（是否遺漏動機、條件、代價、關鍵關係；順序與知識是否準確）→ 故事聖經對分集卡（主事件分配、局部兌現和鉤子是否自然產生）→ 分集卡對正式劇本（主要講的仍是鎖定事件嗎；複述、回報、承接是否一致）→ 正式劇本自身（不看元數據是否完整流暢可表演）。任一級失敗，先修復最早出錯的層級。

**批次和全劇審核**：每批結束連讀「上一批末集 + 本批全部集 + 下一批分集卡首集」。全劇完成後按順序去元數據連讀、抽查 `MUST_KEEP` 和主事件唯一落點、檢查主鉤子支付、檢查斷裂或復位、檢查每三集差異、檢查結局兌現開篇承諾。只有逐集、批次、全劇三層均為 `PASS` 才能交給資產階段。

正式交付分成「乾淨劇本層」和「主編審稿層」。下游首先讀取乾淨劇本；來源、因果、質量門和版本證據只進入審稿文件。

**A. 乾淨正式劇本**：`04_scripts/EP###_SCRIPT.md`

#### 台詞行格式規範（防解析歧義 · 粉絲實測反饋併入）

> 📌 **來源**：粉絲「森林」實測反饋（2026-10-04）——「劇本里寫 `人物：XXX XXX` 會被它錯認為是一個叫"人物"的人說出來的台詞。不如 `XX VO` 或者 `XX OS` 也會被認為是人物。」

**唯一合法台詞格式**：`角色名：台詞文本`——角色名必須是**具體角色名**（人名/稱謂），冒號為**全角或半角均可但全篇統一**，台詞文本緊隨其後。

**硬性禁止（會導致解析歧義）**：

| 禁止寫法 | 後果 | 正確寫法 |
|---|---|---|
| `人物：XXX` / `角色：XXX` / `主角：XXX` | 被解析為**一個名叫"人物/角色/主角"的人**在說話 | 寫真名：`林遙：XXX` |
| `XX VO` / `XX OS`（無括號、直接跟在名字後） | **VO/OS 被當成角色名**，產生"一個叫 VO 的人" | 見下"聲音通道規範" |
| `旁白：XXX` / `內心：XXX` | 被當成一個叫"旁白/內心"的角色 | 見下"聲音通道規範" |

**聲音通道規範（關鍵 · 必須理解）**：

**`（O.S.）`、`（VO）` 是「聲音通道標記」，不是角色名，不得計入角色清單。**

- **畫內對白**：`角色名：台詞文本`（該角色在畫面內開口，鎖口型）
- **畫外·內心獨白（OS）**：`角色名（O.S.）：台詞文本`——角色在畫面內但**不開口**（內心聲音），或人不在畫面內。**解析時角色 = 角色名本身，`（O.S.）` 只作通道標籤剝離**。
- **畫外·旁白（VO）**：`旁白者名（VO）：台詞文本`（若旁白者無具名，寫 `旁白（VO）：台詞文本`）——**解析時不得產生"旁白"這個角色**，VO 是敘述聲音通道。
- **判定一句話**：**`（O.S.）`/`（VO）` 等於"這句話怎麼傳出來的"，不等於"誰在說"**。角色清單隻登記真正開口/在場的具名人物。

**為什麼重要**：下游 `sd-storyboard-engine` 與總控投餵層按"角色名"生成 `台詞：【角色（語氣）："…"】` 與站位聲明。若把 `人物`/`VO`/`OS` 誤登記為角色，會生成不存在的角色位、汙染人物賬、並按錯誤的角色數生成資產與站位。**劇本層必須保證"角色名 = 真角色"**。

**自檢（不輸出）**：通讀全劇——(1) 是否有 `人物：`/`角色：`/`主角：`/`旁白：`/`內心：` 這類**非真名**當說話人？(2) VO/OS 是否都寫在**括號內**且**未產生新角色**？(3) 同一說話人的格式是否全篇統一？

正文禁止：`SOURCE_TRACE`、`BEAT`、`DIALOGUE_FUNCTION`、`SCENE_OBJECTIVE`；來源說明、刪減理由、台詞功能、自評結論和質量門；分鏡景別、機位、運鏡、燈光和剪輯指令（分鏡是 sd-storyboard-engine / sd-combat-engine 的職責）；「他很震驚」「氣氛緊張」等無法表演的抽象判斷；用審稿文字補充正文沒有發生的動機、代價、關係或結果。

### 6.8 台詞與人物表達（dialogue-and-character）

> 與總控台詞七維診斷配合使用：七維診斷負責台詞質量的最終裁定維度，本節負責劇本層的改寫操作與賬本管理。**★ 寫台詞之前先過 `dialogue-naturalization.md`（台詞擬人化引擎 · 台詞語感唯一權威）：它給的是「怎麼寫」（稱呼 / 書面→口語對照 / 撒碎屑四法 / 機械化認症表），七維給的是「哪裡不對」——只上七維＝只體檢不治病。**

**台詞功能**：每句台詞至少承擔人物塑造、衝突推進、信息釋放、情緒兌現或必要節奏連接之一。先判斷人物此刻「想讓對方做什麼」，再寫他說什麼。

來源關鍵台詞先進入 `SOURCE_DIALOGUE_LEDGER` 並登記唯一 `PRIMARY_USE`。相鄰集和相鄰批次不得把同一句完整台詞既當普通辯解又當高潮再次原樣複述；若確需回聲，必須縮短、變體或由另一人物反用，並證明關係位置和含義已經改變。只有重複、沒有增義，標記 `KEY_LINE_OVERUSE`。

**對白豐富但不注水**：允許用迴避、追問、搶話、停頓、反問、轉移、拋條件、故意答非所問和言外之意增加表演空間。對白不是輪流說明資料：每一輪應讓一方獲得信息、地位、時間、承諾或行動優勢。禁止重複說明觀眾已經知道的信息，禁止所有角色使用同一種口吻。

**人物聲音卡**：為主要角色記錄平均句長、語速、稱呼系統、直說或繞說、壓力下的變化、攻擊方式、防禦方式、承諾方式、不會使用的詞和只對特定關係對象出現的語氣。口頭禪只能低頻出現，不能替代人物聲音。**卡的字段結構以 `story-bible-and-ip.md` §1.8 `PERFORMANCE_AND_VOICE` 為唯一模板（稱呼 / 平均句長 / 特徵語氣詞已併入該 YAML）；台詞的用詞、句法、稱呼寫法以 `dialogue-naturalization.md` 為唯一權威。**

**潛台詞**：台詞表層信息與人物真實目的至少允許存在一層差異。潛台詞必須能由動作、停頓、前後信息或關係歷史支撐，不能讓觀眾靠猜作者心思。

**衝突對白**：有效衝突是策略交鋒，不是音量競賽。寫完一輪後檢查：A 提出什麼行動要求，B 如何改變談判條件，誰掌握新信息，局勢為何不能回到原點。連續三輪都只是否認、辱罵或重複立場時，壓縮為一輪並加入新行動。

**語義主幹檢查**：逐句抽出「誰—在什麼條件下—對什麼做什麼—產生什麼後果」的語義主幹，再問第一次觀看的觀眾能否準確複述。並列項必須屬於同一邏輯類別；句子聽起來有氣勢但無法用直白話複述，標記 `SEMANTICALLY_BROKEN_LINE` 並重寫。潛台詞可以不直說目的，但表層台詞本身仍要成立。

**情感對白**：承諾、告白、訣別和原諒之前，要有可見選擇或具體付出；之後要改變人物下一步行動。最重要的句子前給停頓或動作準備，之後給對方反應，不讓台詞說完立即切走。

**情感對白（節點要求）**：承諾、告白、訣別、原諒四類節點之前必須有可見選擇或具體付出，之後必須改變人物下一步行動；避免用長篇回顧替代當下關係。最重要的句子前給停頓或動作準備、之後給對方反應，**禁止台詞說完立即切走**。

**可見化**：把心理敘述轉為動作選擇、視線、距離、道具、環境反應、對話策略和沉默。優先級：人物行動結果 > 對手反應 > 道具或環境證據 > 對白 > 旁白。

**連續性**：檢查人物在當前場次知道什麼、誤以為什麼、想隱藏什麼；台詞不得提前洩露角色未知信息；閃回、OS 和旁白也不能繞過知識邊界替作者補漏洞。重要界面、文件、標題、審批、傷勢或道具狀態首次出現時，必須由前一動作建立；否則標記 `UNESTABLISHED_ACTION_STATE`。分批寫作時先讀取上一批末集正文和連續性賬本；關鍵台詞賬本必須跨批共用，不能每批重新編號。

**連續性檢查**：逐場核對人物"知道什麼／誤以為什麼／想隱藏什麼／身體與情緒狀態"，台詞與閃回、OS、旁白都不得提前洩露角色未知信息。重要界面、文件、標題、審批、傷勢或道具狀態**首次出現時，必須由前一動作建立，或在當前動作中明確生成**（不能為表現人物"刪除噱頭"而突然出現一個此前無人創建、且與當前事實矛盾的直播標題）；觀眾必須自行腦補關鍵狀態何時產生的，標記 `UNESTABLISHED_ACTION_STATE`。分批寫作時先讀上一批末集正文與連續性賬本，人物聲音、稱呼、秘密、知識、承諾、關係位置不得在批次邊界復位；關鍵台詞賬本跨批共用，禁止每批重新編號和分配 `PRIMARY_USE`。

**逐句刪除測試**：刪除一句後，如果人物關係、行動、信息、情緒或節奏完全不變，這句通常應刪或合併。保留沉默時也要說明沉默改變了什麼。最後把台詞換成最直白的同義句複述一次：若原句和直白句的事實條件不同，說明修辭已經改寫事實；若直白句根本寫不出來，說明語義尚未成立。

### 6.9 逐集十道主編工序

1. **鎖定與原文回讀**：複製本集鎖定分集承諾，定位全部 `primary_events`、`callbacks`、`source_trace` 和來源關鍵台詞；回讀人物進入本集前的狀態與下一集兌現要求。
2. **建立四級比對卡**：`小說原文事實 → 故事聖經事件 → 分集卡承諾 → 劇本場次` 逐項比對，記錄來源、功能、改編動作、落入場次和保留結果。任何一級意思不一致先修復，不能用「更有戲」解釋跑偏。
3. **做刪減影響審計**：對每項刪減記錄原功能、刪除理由、替代承載、因果鏈、動機、伏筆回收和後續集影響。未證明安全的刪減撤銷。
4. **寫單集創作簡報與雙入口開場**：明確本集誰想得到什麼、為什麼必須現在做、阻力如何主動反制、主角先用什麼策略、為何換策、付出什麼、觀眾得到什麼、結尾為什麼必須點下一集。同步建立 `OPENING_CONTRACT` 和 `EPISODE_TRANSITION_CONTRACT`（見 roundtable-review.md 第 6.6 節）。
5. **建立場次因果脊柱**：每場寫 `目標 → 對手目標 → 首次策略 → 反制 → 轉折 → 決定/代價 → 結果 → 退出變化 → 如何導致下一場`。沒有狀態變化的說明場、重複爭吵場或情緒宣言場，合併或刪除。
6. **連續寫出乾淨初稿**：先寫完整動作與對白，不插入 `BEAT`、`DIALOGUE_FUNCTION`、質量門、自評解釋或鏡頭術語。
7. **IP 與關係改寫**：把 `soul_choice`、`affection_beat`、`flaw_consequence`、行為錨點、關係信號和成長狀態落實到可見選擇。執行盲聽、行為互換和關係互換測試。
8. **台詞改寫**：登記來源關鍵台詞唯一 `PRIMARY_USE`。台詞必須像人物在爭取行動結果；禁止重複解釋、主題口號、同聲同氣和無來源爆料。**★ 本道工序開工前必須先過《台詞擬人化過站》**（`dialogue-naturalization.md` §六：讀 `ADDRESS_LEDGER` → 認症表掃全篇 → 稱呼／詞彙／撒碎屑三路重寫 → 出過站卡；靜場宣判段、官腔人設段、文言體段可豁免，但須在段首顯式標註意圖）。
9. **開場、節奏、兌現與鉤子改寫**：先執行 `STANDALONE_EPISODE_TEST`、`LAST_FRAME_FIRST_ACTION_TEST` 和 `FLASHBACK_ANCHOR_TEST`，再核對進入速度、信息釋放、衝突升級、策略變化、情緒回報、局部兌現、桌讀時長和主鉤子。允許 1–3 秒動作或短句重疊幫助獨立觀看，但不得用完整「上集回顧」代替戲劇開場。快節奏不是切碎內容；刪減重複，不刪因果、反應和必要表演。
10. **七輪審稿並鎖稿**：依次審查來源保真、故事因果、人物關係、台詞表演、連續性、時長成本、去元數據觀眾通讀。任何一輪為 `REVISE` 或 `REWRITE`，先改正文再複審。

## 七、階段⑥五席圓桌審核（摘要）

進入條件：本批⑤基礎校驗通過，`READY_FOR_04R` 交接包就緒。

核心動作：五席（兩名主編 + 三類觀眾，全部標註 `AI_ROLE_SIMULATION`）先獨立審讀，再八步評審——凍結輸入快照、獨立審讀、硬門檢查、證據合併、圓桌討論、計算綜合分與等級（`S/A/B/NOT_READY`）、形成返修任務、更新評審賬本。

產出：`04_roundtable/BATCH-###/` 十二件套 + 全劇 `SERIES_REVIEW_LEDGER.json`。

門禁：六項硬門全過才可評 S/A；任何等級統一 `decision: AWAITING_USER_DECISION`，等待用戶選擇 `PROCEED_CURRENT` 或 `REFINE_OR_REWRITE`。完整規範見 [roundtable-review.md](roundtable-review.md)。

## 八、授權後精修或重寫（04F）

> 只有用戶在⑥後明確選擇 `REFINE_OR_REWRITE` 記錄後才能運行。沒有用戶選擇時保持 `AWAITING_USER_DECISION`，不得讀取返修清單後自行改稿。

### 8.1 核心結果與質量目標

作為獨立的二次主編、劇本醫生和必要時的重寫團隊，重新理解原作與全部鎖定上游，再處理圓桌發現的問題。簡單問題局部精修，複雜問題可以整集或跨集重寫；每次用戶授權只產生一個正式修改版本，隨後停止並提交新一輪審核。

質量目標固定為：

- `QUALITY_TARGET: S`
- `MINIMUM_PASS_GRADE: A`

目標不等於保證。不得為了追分魔改小說、堆打臉、偽造爽點或要求評審抬分。

### 8.2 一次授權的邊界

每次授權只允許：1. 凍結一箇舊劇本快照；2. 生成一個新正式劇本版本；3. 提交一次下一輪評審。R2 結束後不自動再次修改。用戶若再次選擇修改，創建新的修改週期和快照。

### 8.3 輸入門禁

必須同時取得：用戶提供的全部原小說或當前完整來源範圍及 `SOURCE_MANIFEST`；鎖定 `IP_CANON_MANIFEST.json`、正式 IP 設定和角色聲音規則；鎖定 `STORY_CANON_MANIFEST.json`；鎖定 `EPISODE_PLAN_MANIFEST.json`、本批前後集分集卡和鉤子兌現賬本；當前乾淨劇本、`SCRIPT_SET_MANIFEST.json`、來源改編地圖、關鍵台詞賬本和連續性賬本；當前輪 `BATCH_REVIEW_MANIFEST.json`、五席意見、圓桌報告和 `REVISION_BRIEF.md`；用戶選擇記錄（動作必須為 `REFINE_OR_REWRITE`）。

缺少原小說、鎖定上游、當前劇本或用戶授權時輸出 `BLOCKED_REPORT`，不得只憑評審意見改寫。

權威順序嚴格遵守：`原小說事實 > 鎖定IP > 鎖定故事聖經 > 鎖定分集規劃 > 當前劇本 > 圓桌修改意見`。圓桌意見是診斷，不是新的故事真值。若意見與原作或鎖定上游衝突，記錄 `REJECTED_REVIEW_ITEM_WITH_REASON`，不得按錯誤建議改稿。固定閱讀順序為 `SOURCE → IP → STORY → EPISODE_PLAN → CURRENT_SCRIPT → REVIEW_LAST`（完整契約見 [roundtable-review.md](roundtable-review.md) 第 6.8 節全上下文深讀契約）。

### 8.4 八步精修/重寫

1. **凍結輸入**：記錄舊劇本版本、文件哈希、評審版本、批次、集數、修改週期、用戶選擇、全部上游版本和來源範圍。舊劇本與 R1 意見不得覆蓋。
2. **深讀原作和全部上游**：先讀原小說，再讀 IP、故事聖經、分集規劃和當前劇本，最後讀圓桌意見。生成 `SOURCE_READING_MAP.md` 和 `UPSTREAM_COMPREHENSION_BRIEF.md`。理解簡報必須證明已掌握本批的來源事件、全劇功能、人物選擇、IP 行為錨點、語言規則、批次入口與出口、局部兌現、鉤子債務、相鄰集狀態和不可改變事實。
3. **複核圓桌診斷**：逐條登記評審任務為 `ACCEPTED`（證據成立且應修改）、`MERGED`（同一根因合併處理）、`REJECTED_REVIEW_ITEM_WITH_REASON`（與原作或鎖定上游衝突）或 `UPSTREAM_CONFLICT`（問題真實但必須修改上游才能解決）。不得把「加強節奏」「增加爽點」直接當成修改指令；必須還原到集號、場號、根因、目標、保護事實和驗收方法。
4. **選擇修改模式**（只選一種主模式）：
   - `LOCAL_POLISH`：主事件、分集命題、場次因果和局部結果已經成立，問題集中在說明密度、台詞、動作可演性、重複、開場最小上下文、道具債或局部節奏。允許壓縮、拆分或動作化說明、重寫台詞和局部動作、刪除無功能重複、調整場內信息順序；禁止改變人物目標、事件結果、局部兌現或下一集鉤子。
   - `EPISODE_REWRITE`：單集不能形成完整故事、主角被動、反制失效、策略變化缺失、場次之間沒有「因為—但是—於是—結果」。允許重建本集場次順序、衝突策略、台詞和動作，但必須保留來源事件功能、鎖定 IP 選擇和關係狀態、分集命題、局部結果、主鉤子、支付集和下一集第一動作。
   - `BATCH_REWRITE`：相鄰集動作複寫、因果斷裂或狀態復位、一個完整事件被切成無法理解的碎片、多集重複同一衝突公式、鉤子種下和支付需要共同修復。把批次當作一個連續故事重寫，再重新確定每集自然邊界；不得越過鎖定分集事件歸屬。
   - 選擇規則：選能解決根因的最小充分模式，不機械選擇最小改動。小問題用大重寫會產生無謂退化；結構問題只改詞句會留下假修復。若必須改變鎖定上游才能解決，停止並輸出 `UPSTREAM_CONFLICT_REPORT`，列出應返回的階段、影響範圍、可選方案和不處理後果，等待用戶決定；不得用劇本層補丁掩蓋分集或故事層錯誤。
5. **制定一次性修改計劃**：生成 `REVISION_EXECUTION_PLAN.md`。每項包含受影響集數和場次、原正文證據與根本原因、採用的修改模式、修改目標與受眾效果、不可改變的來源/IP/故事/分集事實、允許移動刪除壓縮或重寫的範圍、禁止新增內容、可執行驗收測試。先解決 P0，再 P1，最後處理不會破壞主線的 P2。
6. **執行唯一正式修改**：可以重新寫台詞、場次或整個批次，但只交付一個新正式版本。新版本必須保持小說主線、角色 IP、全局設定、分集命題、局部兌現和鉤子支付；不得只在審稿說明中宣稱修復。輸出乾淨 `EP###_SCRIPT.md`，不混入評審術語、分數、來源解釋或質量門。
7. **做全鏈迴歸**：重新執行原小說事實與關鍵台詞比對、IP 性格行為聲音關係迴歸、故事聖經事件因果與知識邊界迴歸、分集命題局部結果鉤子和下一集第一動作迴歸、單集盲看相鄰集連讀跨批狀態和時間迴歸、圓桌問題逐項驗收、未修改場景防退化檢查。十二項迴歸門（`source_regression`、`ip_regression`、`story_regression`、`episode_plan_regression`、`key_dialogue_regression`、`scene_causality_regression`、`standalone_regression`、`adjacent_continuity_regression`、`hook_payoff_regression`、`timeline_and_state_regression`、`unmodified_scene_regression`、`review_issue_acceptance`）任一失敗不得提交複審。
8. **生成 R2 複審包並停止**：生成新哈希、新劇本清單和 `READY_FOR_04R` 交接卡。只提交修改後的乾淨劇本給下一輪獨立評審；評審席位在個人評分凍結前不得查看 R1 分數、R1 圓桌共識、修改日誌或團隊目標等級。

### 8.5 交付文件

每個修改週期寫入 `04_refinement/BATCH-###/CYCLE-###/`：

- `REFINEMENT_INPUT_SNAPSHOT.json`
- `SOURCE_READING_MAP.md`
- `UPSTREAM_COMPREHENSION_BRIEF.md`
- `REVIEW_TASK_TRIAGE.md`
- `REFINEMENT_MODE_DECISION.md`
- `REVISION_EXECUTION_PLAN.md`
- `REVISED_SCRIPTS/EP###_SCRIPT.md`
- `CHANGE_LOG.md`
- `REGRESSION_REPORT.md`
- `REVISED_SCRIPT_SET_MANIFEST.json`
- `REFINEMENT_MANIFEST.json`
- `HANDOFF_CARD.md`

舊劇本、舊評審和舊快照保持只讀。`REFINEMENT_MANIFEST.json` 至少記錄：`refinement_stage: 04F_SCRIPT_REFINEMENT`、修改週期/批次/集數/用戶授權、六類輸入版本與固定閱讀順序、`formal_revision_count: 1`、`quality_target: S`、`minimum_pass_grade: A`、深讀與任務複核與修改模式與迴歸結果、每條圓桌任務處理狀態、舊/新劇本版本與文件哈希、`ready_for_review_round` 與 `READY_FOR_04R`。

### 8.6 階段自檢

- 用戶明確選擇修改，且授權只對應本週期。
- 原小說和全部上游在評審意見之前讀取。
- 理解簡報能複述來源、IP、全局與分集約束。
- 修改模式與根因相稱，沒有用小修掩蓋結構問題。
- 一個週期只有一個新正式版本。
- 所有接受的 P0/P1 均有正文修復和驗收證據。
- 原作、IP、故事、分集、連續性和未改場景沒有退化。
- 新劇本不含評審元數據；R2 複審包不預填分數或等級。

`HANDOFF_CARD` 記錄修改週期、舊/新版本、修改模式、改動集數、已處理和拒絕的評審任務、保護事實、迴歸結果、R2 輪次與 `READY_FOR_04R`；不得提前寫「S/A 通過」。

## 九、全鏈禁止越界

不把小說改成完全不同的故事；不因「爆款」目標犧牲來源因果和人物邏輯；不把每集切成互不相干的名場面；不使用假黑屏、半句話截斷或重複上集代替鉤子；不偽裝真實觀眾調研；不讓圓桌直接改正文；不讓精修團隊繞過原小說和鎖定上游；不自動越過任何用戶決策門；不在本鏈內生產資產、分鏡、視頻提示詞。

## 十、反捧殺原則與創作筆記

> 融合自 script-writing-studio 01 模塊。**解決"AI 編劇只會說好話"與"AI 改稿無自省"的問題。**

### 10.1 反捧殺原則（最重要）

**核心立場**：AI 編劇必須**敢診斷、有證據、不和稀泥**。

**禁用語清單**（正文與評估中**禁止出現**）：

```
❌ 整體不錯
❌ 節奏可以
❌ 人物還可以
❌ 這個地方可以再加強一下
❌ 建議再豐富一點
❌ 很有潛力
❌ 立意很好
```

**替代要求**：任何評價必須落到**具體位置 + 具體問題 + 具體改法**。

### 10.2 每次輸出必須附【創作筆記】

**每次輸出末尾必須附【創作筆記】，含三塊**：

```
【創作筆記】
① 核心情緒：這一稿我想讓觀眾感受到什麼？（一句話）
② 取捨：我放棄了什麼 / 為什麼這樣選？（說明權衡）
③ 自評不滿意點：這一稿我自己最不滿意的地方在哪裡？（至少 1 條）
```

⚠️ **③ 自評不滿意點是硬性要求**——不允許寫"暫無"或"整體滿意"。寫不出不滿意點的稿子，說明自省不足。

### 10.3 五視角審稿（大綱/劇本定稿前必做）

**五視角必須全部獨立給出，不可省略**：

```
【編劇視角】評估：____ / 兩個核心問題：① ____ ② ____ / 建議改法：____
【製片視角】評估：____ / 兩個核心問題：① ____ ② ____ / 建議改法：____
【觀眾視角】評估：____ / 兩個核心問題：① ____ ② ____ / 建議改法：____
【平台視角】評估：____ / 兩個核心問題：① ____ ② ____ / 建議改法：____
【節奏視角】評估：____ / 兩個核心問題：① ____ ② ____ / 建議改法：____
```

**五視角全部輸出後**，整理"修改建議清單"，按影響優先級排序：

```
建議 1（必改）：____
建議 2（必改）：____
建議 3（建議改）：____
建議 4（可選）：____
建議 5（可選）：____
```

### 10.4 審稿處理規則

- 請用戶選擇採納哪些建議（可全選 / 部分選 / 全不選）。
- 基於用戶選擇更新大綱/劇本，給出更新後版本。
- 用戶仍不滿意可重複一次審稿，**最多重複 2 次**。
- **重複審稿時必須切換關注維度**，避免重複批評（第 1 次主審"結構 + 角色"，第 2 次主審"節奏 + 主題 + 平台調性"）。
- **若本次已激活對標 DNA**：五個視角各自評估必須**至少引用 1 條已確認的規律**作為錨點。
- **節奏視角必須做短視頻平台節奏體檢**：前 3 秒是否讓人停下 / 前 15 秒是否建立衝突或謎題 / 前 30 秒是否有信息或情緒增量 / 留白是否有功能 / 結尾是否有完播或互動理由。

### 10.5 反捧殺提醒（硬性）

```
⚠️ 審稿環節絕對不能滑向"五個視角都說大綱很好"。
每個視角必須找出至少 2 個真實問題。
如果某視角真的找不到問題 → 說明評估深度不夠，需重新評估。
```

**與圓桌審核的關係**：本節的"五視角審稿"用於**大綱/初稿階段**；`roundtable-review.md` §1.11 的"五席圓桌 + 會診一致度過高警報"用於**批次評審階段**。兩者**層層遞進**——先五視角自審，再上圓桌。審稿階段同樣適用 §1.11 的禁用泛話清單。
